# 実装の進捗

方針: [`improvement-plan.md`](improvement-plan.md) 6 節の段階 0 → 3 の順。各段階の終わりで `make check`(ヘッドレスのサーバ + ボット 2 体で 1 ラウンド完走)が通ることを確認する。

## 段階 0: 土台(2026-10-10)

### やったこと

- プロトコル v2(5.1 節): サーバ → クライアントは改行区切り JSON のプッシュ、クライアント → サーバは `HELLO` / `READY` / `IN` / `BYE` のテキスト行。マップは 1 行 1 文字列。
- サーバの構造を書き直した。受信スレッドは行をキューに積むだけで、main スレッドが 50 ms(20 Hz)の tick ごとに「イベント処理 → `Game::tick` → 全員へ `state` 配信 → 画面描画」を `sleep_until` で刻む。tick はサーバ画面の `getch` に依存しない。
- 移動のサーバ権威化と速度制御(3.6 節): クライアントは方向とボムだけを送り、サーバが `speed` tick ごとに 1 マス進める。1 入力 1 マス。
- 設定の外出し(5.4 節): `--key value` と `server.conf`。`--seed` で乱数固定。
- ヘッドレス(5.3 節): `--no-ui`。makefile が ncurses の有無を自動判定し、なければ `NO_CURSES` でビルド。
- ロビー: 名前一覧、`READY` と全員準備完了からのカウントダウン、`g` で強制開始。ラウンド終了後はロビーに戻る(再起動不要)。名前の重複は `(2)` を付ける。ラウンド中の接続は観戦。
- キルの帰属(炎の持ち主)、同 tick 死亡は同順位、死因付きの結果、`--time` による制限時間。ルールの数値は v1 のまま(7×7、ボム 4、炎 3、導火線 2 秒、炎 1 秒)。
- クライアント: `curses.wrapper`、端末サイズチェック、`--ascii`、矢印 / WASD / hjkl、`q` 2 度押し、ロビー・ゲーム・結果の 3 画面。
- `client/bot.py`(5.6 節の最小版)、`tools/check.py`、トップレベル `makefile`(`make` / `make run` / `make check`)。
- `task1〜3_sample.py` と `keysend.py` を `client/legacy/` に移動。旧オブジェクトモデル用の `test*.cpp` / `sctest.cpp` は削除(新しい構造では使えないため)。
- `docs/README.md` を v2 の起動方法とプロトコルに合わせて書き直した。

### 確認方法と結果

- `make check` を 4 回連続で実行し、すべて `CHECK OK`(seed 1、2 体のボットが 115 tick で相打ち = 同順位 1 位、両ボットが同じ結果を受信)。
- pty 上で `A_client.py` を起動し、ロビー表示 → `r` → ボット参加で開始 → 矢印と `Space` で移動とボム設置 → 死亡表示 → 結果画面(`killed by pbot`)→ `q` で終了、まで動作。全角文字(`２`、`炎`)で描画されることを確認。
- pty 上で ncurses のサーバ画面を起動し、ロビー → ボット 2 体の対戦をマップ表示(`##`、`1`、`o`)→ 結果 → `q` で終了コード 0。
- 生のソケットで `HELLO` → `BYE` → 即切断を 5 回繰り返し、不正な `HELLO 0` を送ってもサーバが落ちないことを確認(初期実装では同じバッチに `BYE` と切断が入ると解放済みポインタを触って落ちたので修正済み)。
- 人間による実機での操作感は未確認。

### 未解決の点

- ソフトブロックも制限時間もない v1 ルールのままだと、ボット同士が出会わずにラウンドが終わらないことがある。`make check` ではサーバに `--time 60` を渡して上限を切っている(段階 1 で制限時間が既定になる)。
- 画面のレイアウトは最小限(HUD は 1 行)。段階 3 で整える。
- サーバ自動発見(UDP)は未実装(段階 2)。クライアントの既定の接続先は 127.0.0.1。

## 段階 1: ゲームの核(2026-10-10)

### やったこと

- マップの人数別プリセット(13×11 / 15×13 / 19×15 / 21×17)、初期位置は四隅(2 人は対角)と各辺の中央。`--legacy-map` で v1 の正方形に戻せる。
- ソフトブロック(可動マスの 60%、2 人は 50%、初期位置とその隣は除外)。壊すと 35% でアイテム(火力 45 : ボム 35 : 速度 20)。アイテムは炎で消える。
- 初期能力 ボム 1 / 炎 2 / 速度 5 tick、上限 6 / 8 / 3 tick。導火線 2.5 秒、炎 0.5 秒。
- 制限時間 120 秒。残り 30 秒からサドンデス(外周から時計回り、開始点はランダム、1 秒 4 マス)。下敷きのボムは消えて持ち主に返る。時間切れは生存者が同順位。
- キルの帰属、自爆、同 tick 死亡の引き分けは段階 0 で入れたものをそのまま使う。結果画面に死因(`killed by X` / `own bomb` / `crushed (sudden death)`)。HUD に残り時間と `SUDDEN DEATH`。
- ボット: 燃えているマスを通らない、サドンデス中は中央へ寄る。

### 確認方法と結果

- `make check`(既定ルール、seed 1〜2)を複数回実行してすべて `CHECK OK`。ラウンドは 35〜50 秒で、キルまたは自爆で決着。
- 4 体のボットで 10 ラウンド連続(`--rounds 10`、seed 7)を回した結果:

| 指標(1 節の目標) | 結果 |
|---|---|
| ラウンド長の中央値 45〜120 秒 | 97.5 秒(最短 37.9、最長 103.2) |
| 15 秒以内の決着 20% 未満 | 0 / 10 |
| 自爆が全死亡の 30% 未満 | 2 / 30(7%) |
| 勝者のアイテム取得数 平均 3 以上 | 2.3 |
| 初期位置ごとの勝率の偏り 2 倍以内 | b1 5 勝、b2 1 勝、b3 2 勝、b4 2 勝(偏りあり。ただしボットは乱数の種で挙動が決まるので、席の有利不利とは言い切れない) |

- 死因の内訳は キル 7、自爆 2、サドンデス 21。ボットが消極的で、時間切れ間際まで生き残る。人間同士では変わるはずで、段階 3 のイベントログで計り直す。
- 2 人ボットの pty 試験で、サドンデスで壁に押しつぶされた側の死因が `crushed (sudden death)` と表示されることを確認。

### 未解決の点

- アイテム取得数が目標にわずかに届かない(2.3 対 3)。アイテム率 35% を 40% に上げるか、ソフトブロックの密度を上げるかは人間のプレイテスト後に決める(5.4 節の設定で再ビルドなしに変えられる)。
- 席ごとの勝率はボットでは評価できない。人間での 4 人×20 戦が必要。

## 段階 2: セッション(2026-10-10)

### やったこと

- ロビーの準備(`READY`)と全員準備完了からのカウントダウン、終了後にロビーへ戻る、観戦者、名前の重複処理は段階 0 で実装済み。段階 2 ではセッションをまたいだときに同じマップにならないよう乱数の種を変えた。
- サーバの LAN 自動発見: UDP ポート 10001 で `BOMBCONSOLE?` に `BOMBCONSOLE <TCPポート> <名前>` を返す(`--discovery 0` で無効)。クライアントは引数なしで起動するとブロードキャストで探し、1 台なら自動接続、複数なら番号で選択、なければアドレス入力。同じサーバが 127.0.0.1 と LAN アドレスの両方で返ってきた場合は 1 つにまとめる。
- サーバは起動時に LAN の IPv4 アドレスを列挙して `clients: python3 A_client.py 192.168.x.y` を表示する。
- README に引数なしの起動、`BOMBCONSOLE_SERVER`、`curl -O` での配布を記載。

### 確認方法と結果

- pty 上で `python3 A_client.py --name pty`(アドレスなし)を起動し、自動発見で LAN アドレス経由の接続 → `r` → ボットと 1 ラウンド → 結果画面で `r` → 2 ラウンド目が同じサーバで始まることを確認。サーバは再起動していない。
- UDP プローブで、ブロードキャスト(255.255.255.255)と 127.0.0.1 の両方に応答が返ることを確認。
- `make check` は `--discovery 0` で UDP を使わずに通る(実行中の本物のサーバと衝突しないため)。

### 未解決の点

- 切断後の同一プレイヤーへの復帰は方針どおり見送り。
